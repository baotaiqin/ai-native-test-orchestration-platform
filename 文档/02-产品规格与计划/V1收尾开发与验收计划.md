## 2. P5-F 第一轮技术决策

### Evidence 失败与终态

- 保持严格的 Evidence 文件、哈希、响应字段及关联校验，不用放宽协议隐藏问题。
- Web 已执行后，Evidence 本地校验、永久协议错误或有限上传重试耗尽应尝试提交安全的 FAILED completion；错误类型固定为 `WEB_EVIDENCE_ERROR`，错误消息固定为“Web 执行证据处理失败”，不透传底层内容。
- 实际步骤 trace 必须保持真实。对有完整真实 trace 的基础设施失败，后端允许步骤均成功而 CaseRun/Run 因证据失败为 FAILED；这是明确的平台失败语义，不能伪造动作失败或伪造 Evidence 成功。
- 该特殊路径只接受 `FAILED + WEB_EVIDENCE_ERROR`，仍必须完整覆盖固定节点、按原严格 trace schema 验证、保留审计。既有普通失败必须包含失败节点的语义不变。取消先取得行锁时继续以取消为准。
- Runner 不因上传失败重跑浏览器；复用 HTTP 已有有限重试与服务端幂等。认证失败停止消费，不能绕过 credential。completion 本身不可达时由服务端超期收敛提供兜底。
- 当前 RUNNING 消息重投会在 claim 收到 409，再映射为 ProtocolError 并拒绝，不会自动重执行 Case。此次不放开 RUNNING 重认领，不引入断点续跑或跨 Runner 迁移。

### 超过执行预算的 Run 收敛

- 复用持久化 `started_at + 生效总超时` 作为执行截止，增加有界上报宽限（建议默认 60 秒）。未开始、缺少可靠截止、尚在截止/宽限内的执行不得收敛。
- 新执行的生效总超时必须固定持久化，执行计划和后台收敛使用同一预算；历史已开始但缺少预算的 Run 不得用当前默认配置推算旧截止，需跳过并另行取证。候选扫描需避免每轮对所有在途 Run 加锁。
- 独立于 Runner 是否在线，扫描已超期的 RUNNING/CANCELLING，行锁后重新校验；未终态 Run、CaseRun、StepRun 在同一事务收口，保留已有真实终态节点和 Evidence，不覆盖正常完成先提交的结果。
- RUNNING 超期为 TIMEOUT/TOTAL_TIMEOUT；CANCELLING 超期为 CANCELLED，区分已有 Force Stop 请求，明确 Cleanup 未确认。不得声称已物理终止远端进程、已完成 Cleanup 或已补齐真实 trace。
- 继续保留现有断线收敛语义，不以 Redis key 缺失推断在线任务失败，不更改正式库结构或手写 SQL 改旧 Run。
- 后台扫描生命周期可停止、每轮 Session 有界、异常不会杀死应用；测试必须关闭真实扫描并注入受控时间/存储。

## 4. 第一轮验收

- Backend：Evidence 平台失败保留真实成功步骤、普通失败语义不退化、取消与正常完成竞态、超时边界、在线/离线/未知心跳、CANCELLING、幂等和敏感信息测试；全量 pytest 与 Ruff。
- Runner：本地 Evidence 校验/上传协议/网络失败；有限重试与 completion 的处置；认证失败停机；completion 响应丢失；不重启浏览器；Slot 与临时目录释放；全量 pytest 与 Ruff。
- MySQL：独立实例空库升级到 head，覆盖自上次真实迁移验收后的 0031～0038 升级/降级/再升级及必要非空数据保护，核对 FK/CHECK/索引；不能仅回退最后一条迁移就声称全部迁移已验。
- 指南：命令、端口、解释器、Worker 类型/Web Slot、Evidence、当前迁移头和当前开发阶段与实际文件一致。

## 5. 证据与完成标准

每轮记录实际修改文件、测试命令/数量、真实外部服务验证、未完成项及原因。主控持续读取全部已派发任务，审查后才结束该轮；需要返工时继续原任务。V1 最终完成必须通过逐项审计，而不仅是自动化全绿。
