## 1. 规则优先级

出现冲突时，按以下优先级执行：

1. 用户最新明确要求；
2. 《AI原生智能测试平台_产品需求系统架构与开发规格说明书》；
3. 本《开发规范与原则》；
4. 《项目开发计划及完成度》；
5. 具体模块设计、接口说明和测试说明。

任何范围、架构或核心技术栈变更，都必须先修改上位文档，再进行实现。不得通过代码事实反向绕过已锁定的规格。

## 2. 当前开发方式

### 2.1 编辑器与本地环境

- **PyCharm** 继续作为项目本机运行、调试和一键启动的主要 IDE；
- 允许用户在同一项目根目录中使用 **VSCode + Claude 插件** 作为 Claude 串行交接时的代码编辑入口；VSCode/插件不改变 Agent 权限、任务范围或验收流程；
- 开发环境以 Windows 为主，Python 使用 3.12；
- 前端、后端和 Runner 均应提供适合在 PyCharm 中直接运行或调试的配置说明；
- 现有 `.run` 配置继续保留，不因使用 VSCode 协作而删除或重写；只有用户明确改为完全使用 VSCode 启动时，才另行设计 `.vscode` 启动配置；
- 文件统一使用 UTF-8 编码，换行符统一为 LF；
- 不依赖个人机器的绝对路径、用户名或仅本机存在的全局配置；
- 中间件优先通过开发用 Docker Compose 启动，前端、后端和 Runner 在本机运行并支持调试；
- PyCharm/VSCode 的个人 UI、窗口、缓存、插件登录和本地偏好属于个人配置，不作为项目功能依赖；
- VSCode Claude 插件不得执行全项目格式化、自动 Git、批量换行转换或无关 Workspace 配置修改。

### 2.2 暂不使用 Git 上传与协作

当前阶段为个人本地开发，**暂不考虑 Git 上传、远程仓库和多人协作流程**。在用户明确调整此规则前：

- 不创建或绑定 GitHub、GitLab、Gitee 等远程仓库；
- 不执行 `push`、`pull`、远程分支、Pull Request/Merge Request 等协作操作；
- 不上传项目代码、文档、配置、数据或 Secret 到外部代码托管平台；
- 不因常见团队规范而强制设计分支模型、Commit 规范、Code Owner 或 Review 流程；
- 如本地已有 Git 元数据，不擅自删除，也不将其连接到远程；
- 关键阶段采用本地备份、变更记录、测试报告和文档版本号保证可追溯性；
- 将来启用 Git 协作时，需先更新本节，再补充分支、提交、评审和发布规则。

### 2.3 文档存放规则

- **所有项目自有文档必须位于根目录的 `文档` 文件夹内**；
- 不在项目根目录、`backend`、`frontend`、`runner` 等目录散落项目说明 Markdown；
- 需求、架构、计划、规范、API 说明、数据库说明、测试说明、部署说明、演示脚本和变更记录均归档到 `文档`；
- 文档文件名使用清晰中文主题，例如 `文档/02-产品规格与计划/项目开发计划及完成度.md`；
- 文档内部引用优先使用相对路径或明确文件名，不写个人电脑绝对路径；
- 第三方依赖自动生成的说明文件不属于项目自有文档，但不得手工修改后冒充项目规范；
- 代码变更影响需求、接口、数据结构、启动方式或验收方式时，必须同步更新对应文档。

### 2.4 Codex、Luna 与 Claude 串行协作

- 项目常态开发架构为 Sol 主控、长期 Luna 执行、必要时动态扩展 Luna；
- Claude 仅是用户手动触发的外部备用 Coding Agent，Sol 和 Luna 均无权自行启用或建议启用；
- 只有用户明确要求切换 Claude 后，Sol 才能停止正常调度并准备本轮专用交接资料；
- Claude 负责文件与 Codex/Luna 负责文件必须串行写入，不允许双方同时修改同一文件；
- VSCode Claude 插件直接操作当前本地工作区，不复制项目；因此 Claude 开始后 Codex/Luna 必须停止本轮文件写入，Claude 结束并停止插件执行后才能返回 Codex Review；
- 当前阶段不使用 Git、branch、worktree 或 commit 完成交接，依靠明确文件边界、状态记录、测试结果和本地备份恢复；
- 用户要求返回 Codex 后，Sol 必须以当前磁盘内容为准重新检查源码、交接结果和测试，不依赖旧聊天记忆直接接受实现；
- Claude 的详细触发、退出、交接和复核流程统一以 `文档/07-协作与历史交接/Codex与Claude串行交接规则.md` 为准；
- `当前开发状态.md` 是 Token 中断时的最小恢复入口，只在明确里程碑和重要变化后更新。

## 3. 范围与版本原则

### 3.1 Scope Lock

- 严格按 V1 → V2 的顺序开发；
- 当前只实现总规格中标记为 V1 的内容；
- V2 和 Out of Scope 内容不得为了“顺手”提前开发；
- 不擅自增加重大框架、基础设施、执行器或业务模块；
- 新需求必须经过“提出 → 必要性判断 → 更新总规格 → 更新版本计划 → 开发”的流程。

### 3.2 深度优先

优先打通一条真实、稳定、可追溯的端到端链路，不追求菜单数量。一个阶段未通过验收，不同时铺开多个后续阶段。

### 3.3 可追溯优先

每次执行必须尽可能追溯：Requirement 版本、Case/Scenario 版本、环境、参数、Runner、Executor、模型、Prompt、AI 原始输出、Step、日志、Evidence、AI 判断及人工复核结果。

## 5. 总体架构原则

### 5.1 职责边界

| 组件 | 核心职责 |
|---|---|
| Vue 3 | 页面、配置编辑、状态展示和人机审核 |
| FastAPI | 业务 API、权限、资产、调度、AI 编排和报告 |
| MySQL | 持久化业务数据、版本与历史结果 |
| Redis | 实时状态、短期事件和在线信息 |
| RabbitMQ | 异步任务排队、路由和消费 |
| MinIO | Screenshot、Trace、日志附件、请求响应等 Evidence |
| Windows Runner | API、Web、SQL、Script 等确定性执行 |
| AI Service | 理解、生成、建议、分析与结构化输出 |

不得混淆组件职责，例如用 Redis 代替历史数据库、用 RabbitMQ 保存最终状态、用 MinIO 承担结构化业务查询。

### 5.2 单体优先

V1 使用模块化单体，不进行微服务拆分。模块之间通过清晰的 Service、Repository、Schema 和领域对象边界隔离，避免为未来可能性提前增加分布式复杂度。

### 5.3 确定性优先

HTTP 请求、变量替换、JSONPath 提取、IF/LOOP、SQL、Cleanup、状态码断言、Schema 校验、Playwright 操作、Retry、Timeout、任务状态和 Evidence 存储必须由程序确定性执行。

## 6. AI 开发原则

### 6.1 AI 的适用范围

AI 可用于需求理解、需求评审、用例生成、Scenario 推荐、录制结果整理、Locator 修复建议、语义断言、失败归因、性能分析和缺陷草稿。

### 6.2 人工确认正式资产

AI 不得直接永久修改 Requirement、Case、Scenario、Locator 或缺陷结论。统一流程为：

```text
AI 建议 → 差异预览 → 人工 Accept / Reject / Edit → 生成正式版本
```

### 6.3 AI 可观测性

每次 AI 调用至少记录：

- 任务类型；
- Provider 与模型；
- Prompt 及其版本；
- 输入摘要和必要的原始输入引用；
- 结构化输出和原始输出；
- Token、费用、延迟；
- Retry、fallback 与错误；
- 人工采纳、拒绝或修改结果。

### 6.4 Prompt 与输出

- Prompt 不得硬编码在业务 Service 中；
- Prompt 必须通过 Prompt Center 管理并版本化；
- 业务型 AI 输出优先使用 JSON Schema；
- Schema 校验失败时按明确策略重试或 fallback；
- AI 结论不得覆盖确定性断言、SLA 或原始指标。

## 7. 后端开发规范

### 7.1 技术基线

- Python 3.12；
- FastAPI；
- Pydantic v2；
- SQLAlchemy 2.x；
- Alembic；
- 异步能力只在有实际收益的 I/O 路径使用，不混用阻塞调用；
- 公共依赖、异常、日志和配置集中管理。

### 7.2 模块分层

每个业务模块优先采用：

```text
module/
├── router.py       # 路由、依赖注入、输入输出协议
├── schemas.py      # Pydantic Schema
├── service.py      # 业务用例与事务编排
├── repository.py   # 数据访问
├── models.py       # ORM Model
├── enums.py        # 模块枚举
└── domain.py       # 需要时使用的领域对象/规则
```

强制规则：

- Router 不直接写 SQL，不直接访问 MQ、Redis、MinIO 或模型 Provider；
- Router 不承载复杂业务流程；
- Service 负责业务规则和事务边界；
- Repository 只负责数据访问，不返回 HTTP 响应；
- ORM Model 不直接作为外部 API 响应；
- 跨模块调用通过公开 Service 接口，禁止随意访问其他模块内部 Repository；
- 公共工具保持无业务含义，禁止形成无边界的 `utils.py` 垃圾箱。

### 7.3 Python 风格

- 公共函数、方法、类和数据结构必须有类型标注；
- 命名使用 `snake_case`，类名使用 `PascalCase`，常量使用 `UPPER_SNAKE_CASE`；
- 函数保持单一职责，复杂分支拆分为可测试的小函数；
- 禁止使用大量 `print()` 代替日志；
- 不使用裸 `except:`，捕获明确异常并保留异常链；
- 不在默认参数中使用可变对象；
- 时间统一存储为 UTC，展示层按用户时区转换；
- 枚举、状态和错误码集中定义，禁止散落魔法字符串；
- 注释解释“为什么”，代码本身表达“做什么”。

### 7.4 API 规范

- API 统一使用 `/api/v1` 前缀；
- URL 使用资源名复数和小写短横线；
- 输入输出由 Pydantic Schema 显式定义；
- 分页、排序、过滤和时间格式保持一致；
- 创建、修改、删除、执行等操作必须校验权限；
- 统一错误响应包含错误码、可读消息和可选详情；
- 不向客户端返回内部堆栈、Secret、数据库密码或 Provider Key；
- 幂等要求明确，Runner 心跳、事件上报和状态更新必须可安全重试；
- API 行为发生变化时同步更新 `文档` 内的接口说明。

### 7.5 数据库规范

- 数据结构变更统一通过 Alembic Migration；
- 禁止绕过迁移手工修改正式库结构；
- 表名和字段名使用 `snake_case`；
- 业务表至少按需要包含主键、创建时间、更新时间；
- Project 级资产必须校验 `project_id` 边界；
- 删除默认采用归档或软删除，物理删除仅限明确的危险操作；
- 版本化资产保存实际 Version ID，Run 不只引用“当前版本”；
- 大 JSON 适合保存快照，不参与高频过滤；
- `project_id`、`status`、`created_at`、`run_id`、各类关联 ID 等按查询模式建立索引；
- Migration 必须同时提供升级路径，并在空库和已有数据场景验证。

## 8. 前端开发规范

### 8.1 技术基线

- Vue 3 Composition API；
- TypeScript；
- Vite；
- Element Plus；
- Pinia；
- Vue Router；
- Axios；
- ECharts；
- SQL、Python、JSON 等高级编辑场景使用 Monaco 或 CodeMirror。

### 8.2 代码组织

- 页面放在 `views`，可复用界面放在 `components`；
- HTTP 请求集中在 `api`，页面组件不散写请求地址；
- 跨页面共享状态放在 Pinia，本地临时状态保留在组件；
- 可复用业务逻辑放在 `composables`；
- API DTO、领域类型和枚举放在 `types`；
- 路由按业务模块组织，并使用权限守卫；
- 避免超大单文件组件，表单、列表、详情、编辑器按职责拆分。

### 8.3 TypeScript 与交互

- 禁止以大量 `any` 绕过类型系统；确需使用时必须限制范围并说明原因；
- Props、Emits、接口响应和表单模型必须有明确类型；
- 页面必须提供 Loading、Error、Empty 三类状态；
- 保存、执行、删除、强制停止等操作必须有清晰反馈；
- 危险操作需要二次确认，并明确对象与影响；
- Secret 默认不可回显；
- AI 建议与正式资产必须在视觉和交互上明确区分；
- 实时日志页面应处理断线、重连、完成和取消状态；
- 表单校验应在提交前完成，后端仍需重复执行可信校验。

## 9. Runner 与执行器规范

### 9.1 Runner 边界

Runner 是执行核心，不承载资产管理页面或复杂业务审批。Runner 只接收经过校验且版本固定的任务快照，并上报状态、日志、结果和 Evidence。

### 9.2 Executor 接口

执行器统一提供类似以下生命周期：

```python
class BaseExecutor:
    async def prepare(self, task, context): ...
    async def execute(self, node, context): ...
    async def cancel(self): ...
    async def cleanup(self, context): ...
    async def collect_artifacts(self): ...
```

### 9.3 执行规则

- Run 创建前执行 Environment、Secret、Runner、Capability、Tag、Slot、DSL、变量、数据源等校验；
- 校验失败的任务不得进入 RabbitMQ；
- 每个 Run、CaseRun、StepRun 使用唯一 ID；
- 状态迁移必须符合已定义状态机并支持幂等上报；
- 自动 Retry 只到 Step 级且默认最多一次；
- Retry 不适用于明显有副作用且无法保证幂等的操作；
- Cancel 允许当前步骤安全结束，Force Stop 立即终止并记录风险；
- Cleanup 应在成功、失败、取消等路径尽可能执行并单独记录结果；
- Resource Registry 按 LIFO 顺序清理；
- Runner Token 一次展示、可撤销、不可写入日志；
- V1 只保证 Windows + Chrome，其他操作系统或浏览器不提前实现。

## 10. 配置、Secret 与安全规范

- 配置分为默认配置、环境配置和 Secret，禁止混为一体；
- 真实密码、Token、API Key、Cookie、数据库凭据不写入代码或项目文档；
- `.env` 只保存本地或部署配置，不在示例中放真实 Secret；
- Secret 加密存储，API 默认不回显明文；
- Windows 本机开发阶段使用 DPAPI + 应用密钥加密 Secret；正式容器部署前必须替换为跨平台密钥服务或经过审计的加密 Provider，不允许降级为 Base64、明文或自制弱加密；
- 日志必须对 Authorization、Cookie、password、token、api_key 及自定义 Secret 变量脱敏；
- 密码使用可靠 Hash，不可逆加密；
- 文件上传限制类型、大小和文件名，并避免路径穿越；
- MinIO Bucket 默认私有，下载走授权 API 或短期签名 URL；
- Python Script 设置超时、资源限制和允许范围；
- SQL 连接使用最小权限账号；
- Web/Runner/AI 外部输入均视为不可信并做校验；
- 不在错误响应和前端控制台暴露堆栈或凭据。

## 11. 日志、错误与 Evidence 规范

### 11.1 结构化日志

日志至少包含可用的上下文字段：

```json
{
  "timestamp": "...",
  "level": "INFO",
  "run_id": "...",
  "case_run_id": "...",
  "step_run_id": "...",
  "runner_id": "...",
  "event": "HTTP_REQUEST",
  "message": "...",
  "metadata": {}
}
```

### 11.2 错误处理

- 使用总规格定义的平台级、API、Web 错误码；
- 用户可理解的消息与内部诊断信息分离；
- 异常不得静默吞掉；
- 外部系统、AI Provider、MQ、存储和数据库错误要保留分类；
- Cleanup 失败不能覆盖原始执行失败，但必须单独记录。

### 11.3 Evidence

- Evidence 与 Run/CaseRun/StepRun 关联；
- 请求响应、截图、Trace、控制台、网络日志、AI 原始输出等按类型存储；
- 大文件放 MinIO，MySQL 保存元数据和引用；
- Evidence 文件名、类型、大小、Hash、创建时间和来源 Step 可追溯；
- Evidence 中同样执行 Secret 脱敏和访问权限控制。

## 12. 测试规范

### 12.1 测试层级

- 单元测试：领域规则、变量、DSL、状态机、解析器、断言和工具函数；
- 集成测试：数据库 Repository、API、MQ、Redis、MinIO 和 AI Gateway 适配层；
- 契约测试：前后端 DTO、Runner 协议、任务快照与事件格式；
- 端到端测试：Requirement/Swagger → Case → Run → Evidence → Report；
- 回归测试：每个 Phase 的验收场景和历史缺陷。

### 12.2 测试要求

- 修复缺陷时先补充能复现问题的测试，再验证修复；
- 测试数据独立，不能依赖执行顺序；
- 外部 AI、对象存储和被测服务在单元测试中使用可控替身；
- 核心链路必须保留至少一条连接真实开发中间件的集成验证；
- 断言应验证业务结果，不只验证 HTTP 200；
- 测试产生的数据必须 Cleanup；
- 不为了覆盖率数字编写无意义断言；覆盖率用于发现盲区，不作为唯一质量指标。

## 13. Definition of Done

普通功能只有同时满足以下条件才算完成：

- [ ] 范围符合当前版本；
- [ ] 数据库 Migration（需要时）；
- [ ] Backend API 与 Pydantic Validation；
- [ ] 权限校验；
- [ ] Frontend 页面与交互；
- [ ] Loading、Error、Empty State；
- [ ] 结构化日志和统一错误码；
- [ ] 单元测试或核心集成测试；
- [ ] `文档` 内的说明已更新；
- [ ] Demo 场景验证通过。

Runner 功能还必须具备：

- [ ] Cancel；
- [ ] Timeout；
- [ ] Retry 策略；
- [ ] Evidence；
- [ ] Secret Mask；
- [ ] 状态机和异常路径验证。

AI 功能还必须具备：

- [ ] Prompt Version；
- [ ] Model 记录；
- [ ] Structured Output；
- [ ] Raw Output；
- [ ] AI Call Log；
- [ ] Error/Retry/Fallback；
- [ ] 人工确认或确定性结果边界。

未满足全部适用条件的功能只能标记为“进行中”或“待验收”，不能计为 100%。

## 14. 文档与进度维护

### 14.1 文档更新触发条件

出现以下任一情况必须更新文档：

- 需求、版本范围或验收条件变化；
- 技术栈、目录结构或架构职责变化；
- 数据表、API、Runner 协议、状态机或 DSL 变化；
- 启动、配置、部署或依赖方式变化；
- 完成一个阶段或重要功能；
- 新增重大风险、限制或技术决策。

### 14.2 进度更新原则

- 进度以验收通过的子项为依据；
- 不以创建文件、代码行数或页面截图认定完成；
- “待验收”最高按 80% 计算；
- 完成一个 Phase 后更新《项目开发计划及完成度》的看板、里程碑和记录；
- 文档中的“已完成能力”必须与实际可运行结果一致。

---

## 15. 变更与决策流程

重大变更包括：新增框架、更换数据库或 MQ、修改版本范围、改变 Runner 协议、改变 AI 正式资产原则、引入新执行器或开发 Out of Scope 内容。

统一流程：

```text
提出问题或需求
      ↓
说明目标、收益、成本、风险与替代方案
      ↓
确认是否属于当前版本
      ↓
更新总规格与本规范/开发计划
      ↓
实现、测试、Demo 验证
      ↓
记录实际结果
```

小型实现细节可直接在当前规格范围内决定，但不得改变外部行为、数据兼容性或安全边界。

## 16. 禁止事项速查

开发中禁止：

1. 未经确认扩展 Scope 或跳版本开发；
2. 未经确认上传 Git、连接远程仓库或开展协作流程；
3. 在 `文档` 文件夹外散落项目自有文档；
4. 在 Router 中混写数据库、AI、文件、MQ 和复杂业务流程；
5. 绕过 Alembic 手工修改正式数据库结构；
6. 在代码、日志、Evidence 或文档中泄露 Secret；
7. 把 Prompt 硬编码在业务 Service；
8. 让 AI 替代确定性的变量、IF、断言、SLA、状态机或 Cleanup；
9. 让 AI 自动永久修改正式 Case、Scenario 或 Locator；
10. 只实现成功路径，不处理权限、异常、取消、超时与清理；
11. 使用大量 `print()`、魔法字符串、裸异常和无类型边界；
12. 把“代码已写”标记为“功能已完成”；
13. 为未来可能性提前进行微服务、Kubernetes、多浏览器或跨平台 Runner 设计；
14. 删除或覆盖不属于当前任务的本地文件与用户修改。

```text
深度优先，闭环优先。

AI 建议先预览，正式资产由人工确认。

每次执行固定资产版本并保留完整 Evidence。
所有项目文档放入“文档”文件夹。
当前使用 PyCharm，本地个人开发，暂不上传 Git 或开展远程协作。
完成必须可测试、可验收、可演示、可追溯。
```
