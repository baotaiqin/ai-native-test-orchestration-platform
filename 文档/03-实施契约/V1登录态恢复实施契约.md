# V1 登录态恢复实施契约

2026-09-10 主控设计，尚未实施或派发。依据总规格第40节：登录态失效后自动执行绑定登录流程、更新 Storage State、原步骤重试一次。P5-E 当前单 CLICK 场景不提供此能力的验收证明。

## 已核实的缺口

- `web_cases/models.py` 的 SessionProfile 保存加密 Storage State、环境、到期时间和更新时间，没有绑定登录流程。
- `web_cases/schemas.py` 的创建/修改接口没有登录绑定或过期检测规则。
- `runs/service.py` 在 Validate 和 execution-plan 两处直接拒绝已到期 Profile；没有恢复计划。
- `runner/executors/web.py` 只在创建 Browser Context 时载入 Storage State，没有重新登录和刷新回传。

## 实施行为

1. Profile 可绑定同项目的已批准 Web Case 固定版本作为登录流程；同时配置明确的过期判断条件，例如登录页 URL 或登录表单 Locator。不得用任意 Timeout、业务断言失败或 LLM 猜测代替过期判定。
2. 登录流程的固定版本不允许再引用 Session Profile，避免递归恢复；参数/Secret 仍通过已有受控 Resolver 解析，登录密码不得写入普通参数或日志。
3. Profile 已到期且没有可用登录绑定时继续拒绝运行；存在合法绑定时允许生成包含恢复计划的执行计划，不能把已过期 Storage State 当作有效会话使用。
4. 运行中通过已配置条件确认过期时，执行固定登录流程，确认登录成功，刷新同一 Browser Context 的 Storage State，再重试原步骤一次。恢复原因可单独审计，但原业务步骤与其它自动重试共享V1最多一次的总上限，不能在已用过一次网络/自愈重试后再额外重放；计数不可因进程内重新进入函数清零。详见《V1步骤重试上限实施契约》。
5. 登录流程与恢复重试共享原 Run 总预算和 Cancel/Force Stop 信号。不得延长持久化总超时，也不能以重新创建 Run/浏览器无限重试绕开预算。
6. 对可能已经产生副作用的操作须保留真实尝试记录；不能把一次恢复隐藏成从未尝试过的步骤。普通 Locator 缺失仍走 Locator 诊断，不自动登录。

## 后端与 Runner 契约

- 后端 execution-plan 固定 Profile ID、当前状态指纹或修订号、登录 Case/Version、已校验的检测/成功条件及恢复预算。消息队列仍只传既有稳定标识，不能放 Storage State、登录 DSL 或 Secret。
- 恢复后的 Storage State 仅通过受 Runner credential 保护的专用回传通道提交；后端必须检查该 Runner 正在执行的 Run、Profile 的项目/环境归属、未归档状态及计划中的原修订号。
- 使用比较原修订号再更新的方式，避免迟到执行覆盖用户手动更新或另一已完成刷新。冲突不得静默覆盖，应返回固定安全代码；当前浏览器已取得的有效会话与持久化失败分开记录。
- 原始状态仅出现在受控执行计划/刷新传输和内存处理路径，数据库继续加密。不能把状态塞入 completion trace、Evidence、AI快照、SSE、队列或普通错误信息。
- 隔离子进程到父进程的刷新数据须有大小与结构限制、明确消息类型和清理生命周期。不能复用任意调试日志回传，不能关闭全局脱敏。
- 记录恢复开始/成功/失败、固定登录版本、Profile 修订前后、安全错误类型与耗时；不伪造正常 Case 步骤，也不把登录成功当作原业务步骤成功。

## 前端

Profile 编辑提供明确的登录流程绑定、固定批准版本、过期及成功条件；展示设置是否可用。Run 详情能看到恢复行为与失败原因，仍不展示 Cookie/Storage State 正文。后端 Schema/接口验收后再派前端接入，不让两端通过互发消息临时改契约。

## 验收

- 未过期复用、已知过期、运行中跳回登录、未配置绑定、绑定归档/未批准/跨项目/环境冲突、递归绑定拒绝。
- 真实 Chrome：登录→保存状态→目标端主动失效→恢复登录→原步骤成功；核对登录计数及原步骤最多一次恢复重试。
- 登录失败、检测误匹配防护、重复过期、Cancel/Force Stop/总预算耗尽，均无无限循环或重复业务运行。
- 状态更新授权、修订冲突、归档竞态、重复/迟到回传、超大/非法状态；原历史不可被覆盖。
- RabbitMQ、SSE、日志、错误、Evidence 与 AI 快照中不出现注入的合成 Cookie/Storage State/密码标记；原始状态只在受控路径出现。
- 新迁移在独立 MySQL 升级/降级/再升级并带现有 Profile 数据；既有未配置恢复的 Profile 行为保持明确。
