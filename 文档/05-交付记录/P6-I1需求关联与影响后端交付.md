## API 契约

所有新接口均位于 `/api/v1`，要求当前用户至少可访问关联项目；创建和移除要求项目写权限，并受项目、需求和目标资产归档门禁约束。

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/requirements/{requirement_id}/links` | 创建精确、活动中的需求关联 |
| `GET` | `/requirements/{requirement_id}/links` | 按关联 ID 升序分页读取；`include_removed=true` 可读取历史 |
| `DELETE` | `/requirements/{requirement_id}/links/{link_id}` | 状态化移除，保留原记录、版本与审计信息 |
| `GET` | `/requirements/{requirement_id}/impact` | 按显式 RequirementVersion ID 比较并分页返回确定性关联范围 |
| `GET` | `/test-cases/{asset_id}/requirements` | 原 TestCase 反向需求追溯 |
| `GET` | `/web-cases/{asset_id}/requirements` | 独立 WebCase 反向需求追溯 |

创建请求使用显式类型和版本 ID，例如：

```json
{
  "asset_type": "WEB_CASE",
  "asset_id": 17,
  "requirement_version_id": 31,
  "asset_version_id": 44,
  "relation_type": "COVERAGE",
  "confidence": 1.0
}
```

`asset_type` 仅允许 `TEST_CASE` 或 `WEB_CASE`。服务会校验需求版本、资产和资产版本的真实归属及同项目关系；错误归属、归档写入、重复活动关联和并发唯一性冲突均拒绝，不覆盖旧记录。

影响查询示例：

```text
GET /api/v1/requirements/9/impact?from_version_id=31&to_version_id=35&page=1&page_size=20
```

响应在 `comparison` 中同时返回两个版本的 ID、版本号、内容哈希、`content_changed`、增删行数；每个关联条目分别返回：

- `selected_scope_status/reason`：用户选定 from/to 的比较范围；
- `recorded_baseline_status/reason`：该链接自身记录的需求基线到目标版本的判断；
- 资产和资产版本状态、可靠引用、当前版本 ID、关联状态和审计字段；
- `created_at_time_basis` 明确为 `UTC` 或 `LEGACY_UNKNOWN`；可靠新时间带 `Z`/`+00:00`，旧来源未知时间不伪造 offset；
- `removed_at_time_basis` 在移除时间存在时为 `UTC`；
- `historical_scope=CURRENT_ASSOCIATION_NOT_RUN_SNAPSHOT`，明确当前关联不是历史 Run 的需求快照。

状态为 `NO_CHANGE`、`POSSIBLY_OUTDATED` 或 `BASELINE_UNKNOWN`。潜在过时仅表示“确定性关联范围，尚未经人工确认实际受影响”，不会修改资产/版本状态，不会触发 AI、审批或运行。

既有 `/requirements/{id}/diff` 继续使用版本号参数；新影响接口明确使用版本 ID。Diff 现在按统一差异结构跳过两个文件头，因此正文的 `+++`、`---`、`++`、`--` 能正常计数，正向、反向、相同内容和空内容行为确定。

## 并发与事务边界

- 三种写入共用锁序：`Requirement FOR UPDATE → 当前活动关联 → 最近 REMOVED 前驱 → 修改/提交`。Requirement 使用 `populate_existing` 当前锁定读，即使 Session identity map 中已有对象也刷新真实状态。
- 活动关联和最近移除前驱均为 `SELECT ... FOR UPDATE`。因此在默认 REPEATABLE READ 下，即使调用方较早建立了一致性读视图，前驱判断仍使用当前读，不把用户选择的旧快照误当真实关联状态。
- 移除目标的 `SELECT ... FOR UPDATE` 同时启用 `populate_existing`。数据库当前读返回的 REMOVED 状态会覆盖 Session identity map 中的旧 ACTIVE 属性；不使用 `expire_all`，也不影响其他缓存对象。
- Requirement 行作为稳定串行化锚点；同一需求下的关联写入按同一顺序进入。列表、反向查询和影响查询不增加写锁。
- 写事务保护范围从首次锁定查询持续到 `commit`。查询、flush 或 commit 出现 PyMySQL 1205（锁等待超时）或 1213（死锁受害）时，Session 先 `rollback`，HTTP 返回不含 SQL/驱动详情的 409；调用方可自行重试，本服务不重放业务写入。
- 其他 OperationalError 会回滚 Session 后原样交给全局错误边界，不笼统转成业务冲突。IntegrityError 继续使用原有重复/并发冲突语义。
- `commit` 成功后的 `refresh`/响应批量读取位于回滚映射之外；若此阶段失败，不会谎报之前写入已经回滚。服务级回归验证该行仍已提交。
- 旧关联行、精确版本、UTC/旧未知时间、ACTIVE 唯一性、移除历史与 supersedes 链均保持不变。
