## 实施结论

Backend 已把“新正式 API Case Version / 新 API_CASE 执行”的 Step 自动重试上限收口为
严格 `0/1`，同时保留历史数据读取边界：

- `0`、`1` 可新建、创建新版本、批准 AI 建议并执行；
- `bool`、负数及大于 `3` 的值由严格请求 Schema 拒绝；
- 历史 Schema 继续解析整数 `2/3`，但新建、更新和批准正式版本时以稳定 `409` 拒绝，
  不 clamp、不创建半成品、不改变当前版本指针；
- 历史 API Case Version、AI 建议、Run、CaseRun、StepRun、执行结果与报告中的 `2/3`
  原样读取，不迁移、不回写；
- 旧版本的新执行在 Validate/Create/Dispatch/Claim/Plan/Start 各阶段都不能绕过；
- Dispatch 在创建 Outbox 和调用 MQ publisher 之前重检，拒绝时保持 Run 为 `CREATED`，
  不产生消息；Claim 拒绝时保持 `QUEUED` 且不写 claimed 字段；
- Plan/Start 拒绝时保持 `ASSIGNED`，不开始 CaseRun/StepRun、不产生执行结果或 Evidence；
- 已经进入 `RUNNING` 或 `CANCELLING` 的旧任务继续按锁定历史策略完成/取消；已有完成
  结果优先幂等返回，不能被后续 V1 门禁破坏。

稳定错误如下：

- code：`API_STEP_RETRY_LIMIT_EXCEEDED`
- message：`V1 API Step 自动重试最多一次；请将 max_retries 设为 0 或 1，并创建符合 V1 的新版本`
- details：`{"maximum": 1, "remediation": "CREATE_NEW_CASE_VERSION"}`

Run Validate 以同一 code 作为 issue 返回；Run Create 仍保持外层
`RUN_VALIDATION_FAILED`，其 `details` 中包含该稳定 issue。

## 代码实现

### `backend/app/modules/test_cases/retry_limit.py`

- 新增 V1 写入/执行边界及稳定错误定义；
- 使用 `type(value) is int`，明确排除 Python `bool`；
- 独立于历史读取上限 `3`，避免共享响应 Schema 被错误收窄。

### `backend/app/modules/test_cases/schemas.py`

- `ApiRetryPolicy.max_retries` 保持历史读取兼容 `0..3`；
- 增加严格整数校验，禁止 `bool` 被 Pydantic 当作 `1` 接受；
- 未将共享 `SuggestedCase`/详情响应 Schema 改成 `le=1`。

### `backend/app/modules/test_cases/service.py`

- 手工创建 Case、创建 Case Version、单个 AI 建议批准、批量 AI 建议批准统一经过
  V1 正式写入门禁；
- 批量批准遇到任一 `2/3` 时整笔事务回滚，不留下已批准建议或正式 Case。

### `backend/app/modules/runs/service.py`

- Validate/Create 对锁定 API Case Version 检查 `0/1`；
- Dispatch、Claim、Execution Plan、首次 Execution Start 再次检查，覆盖校验后数据漂移；
- 已发布消息的幂等 Dispatch、已认领的幂等 Claim、已开始的幂等 Start 保留原安全语义；
- `RUNNING/CANCELLING` 的执行计划允许读取历史策略以便收尾；
- Completion 在历史策略模式下核对 `retry_count`，并在任何策略校验前优先返回已存在的
  幂等结果。

## 历史兼容证据

- 直接保存的历史 `max_retries=3` 经 Case 详情与版本列表读取后，原始 JSON SHA-256
  不变；
- 编辑状态的 AI 建议可原样保存和读取 `2/3`，批准失败后建议内容、状态、关联 Case ID
  均不变；
- 报告固定数据使用 CaseRun、StepRun 和 RunApiExecutionResult 的 `retry_count=3`，API
  报告三个位置均返回 `3`；
- 已启动任务把锁定版本模拟为历史 `2` 后可用 `retry_count=2` 完成；随后把版本模拟为
  `3`，重复 completion 仍先返回已持久化的 `2`，且标记 `idempotent=true`；
- `CANCELLING` 任务可按历史 `2` 完成取消；超过其历史上限的 `3` 仍拒绝。

所有历史兼容测试仅使用进程内 SQLite 和假 MQ/ObjectStore，不触碰正式数据库、队列、
对象存储或业务 Run。

## 前端接入边界

后续 Frontend 包应按以下后端契约接入：

- 新建/编辑/批准界面的 `max_retries` 仅提供 `0/1`，文案说明“最多额外重试一次，
  总尝试最多两次”；
- 历史详情仍要原样展示 `2/3`，不能在表单初始化时 clamp 成 `1`；历史旧版本的执行
  操作应禁用并引导“创建符合 V1 的新版本”；
- 正式写入、Dispatch/Claim/Plan/Start 的直接错误 code 为
  `API_STEP_RETRY_LIMIT_EXCEEDED`；Run Create 的外层 code 为 `RUN_VALIDATION_FAILED`，
  需从 `details[].code` 识别同一原因；
- `422` 表示类型/范围本身非法（如 `bool`、负数、`>3`），`409` 表示历史可读但不允许
  新写入或新执行的 `2/3`；
- 不自动改写历史版本，不在客户端失败后静默重试旧版本。
