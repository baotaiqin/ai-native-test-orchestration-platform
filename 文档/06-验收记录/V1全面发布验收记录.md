## 7. 同日发布续验

### 7.1 独立 MySQL 与认证稳定性

- 在一次性 `mysql:8.4` 容器的唯一 Schema 中完成空库到 `0076`、`0076 → 0077`、`0077 → 0076`、`0076 → head`，两次 `alembic check` 均返回 `No new upgrade operations detected.`；`performance_analyses` 实测 21 列、5 外键、4 CHECK 与 2 条目标唯一约束，Schema 已由脚本清理。
- 真实 MySQL 登录后立即访问 `/auth/me` 的 50 次诊断中复现 26 次 401。根因是 MySQL `DATETIME(0)` 对微秒四舍五入，而 JWT 时间戳向下取整，导致会话签名时间偶发相差 1 秒。登录服务改为在持久化与签名前统一到同一整秒，并增加 `.999999` 边界回归；修复后真实 MySQL 连续 100 次登录→`/auth/me` 为 100/100 成功。

### 7.2 真实性能主流程

- 注册独立 Windows Runner，经 DPAPI 保存身份并通过 RabbitMQ 实际消费。续验发现 Runner 心跳把 PERFORMANCE 可用 Slot 固定上报为 0，且 SSE/JMeter readiness 与真实探测不一致；修复后 Runner 上报 PERFORMANCE available=1，READY 能力包含 API、JMETER、SCRIPT、SQL、SSE、WEB。
- Python HTTP/SSE 真实链路通过：2xx 6/6 成功且 2 次 Warm Up 未计入；418、503、请求超时、主动断连分别精确归类为 `HTTP_418`、`HTTP_503`、`TARGET_TIMEOUT`、`TARGET_NETWORK_ERROR`；SSE 2/2 成功，记录 TTFT 与 6 个 chunk。SLA 通过/失败、历史列表和双 Run 对比均由后端实际持久化验证。
- JMeter 实际执行 4/4 成功，SLA 通过。Scenario 性能续验先发现普通 Scenario 分支优先于 PERFORMANCE 模式，继而发现性能入口错误调用 API start；两处均已修复并新增回归。最终 Scenario 性能 3/3 成功，指标、错误分布和 SLA 正常落库。
