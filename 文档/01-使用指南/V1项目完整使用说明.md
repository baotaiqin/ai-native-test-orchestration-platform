## 1. 平台能做什么

本平台把需求、接口契约、测试资产、执行器、执行过程和结果审计放在同一条链路中，主要支持：

- 从 Markdown 需求或 Swagger/OpenAPI 契约建立可追溯的测试来源；
- 使用 AI 评审需求、生成 API Case、API Scenario 或整理 Web 录制结果；
- 由人工编辑、接受、拒绝和批准 AI 产物，AI 不会直接发布正式测试资产；
- 编写和执行 API Case、API Scenario、Web Case；
- 使用 CSV、Excel、Faker、MySQL 只读查询等数据集做数据驱动测试；
- 通过 Windows Runner 执行真实 HTTP、SQL、Python 受限脚本和 Playwright/Chrome 操作；
- 实时查看运行状态，取消或强制停止异常任务；
- 保存截图、Trace、日志等证据，并生成统一报告、AI 失败分析和缺陷草稿；
- 对失败的 Web Locator 生成自愈候选，经验证和人工接受后产生新草稿版本；
- 通过不可变版本、项目权限、Secret 加密、AI 调用日志和来源快照保证审计性。

V1 不包含对外部缺陷系统的自动提交、Windows Service、多任务高并发调度或 V2 规划功能。

## 2. 先理解五个核心概念

### 2.1 项目是主要隔离边界

需求、API 定义、用例、数据集、编排、Web 资产、运行、证据、报告和模型绑定都归属于项目。现在应先在“项目门户”选择项目并点击“进入项目”，再在专属工作区创建或查看资产；项目上下文会跟随地址和顶部项目栏传递，不需要在每个业务页面重复选择。

项目归档后保留历史资产、运行、证据和报告供查询，但不能继续创建新运行。需要继续使用时，由有权限的用户恢复项目。

### 2.2 资产状态和不可变版本

可执行资产都采用版本化管理，但 V1 中不同资产的可执行状态略有区别：

1. API Case 由人工创建或接受建议后成为 `ACTIVE`，运行中心使用其当前固定版本；归档后不可再创建新 Run；
2. Scenario 和 Web Case 先处于 `DRAFT`，必须人工批准为 `APPROVED` 后才能执行；
3. 编辑会创建新版本，不覆盖已经用于历史运行的版本；
4. Scenario/Web Case 新建版本后会重新回到草稿状态，需要再次批准；
5. 历史 Run 永远指向当时执行的固定版本和来源快照。

因此，“AI 建议已接受”后仍要到对应资产页面检查完整运行配置。Scenario/Web Case 还必须批准；API Case 没有单独批准按钮，但必须保持 `ACTIVE` 且当前版本通过运行前校验。

### 2.3 预览不等于真实执行

资产页中的校验、渲染预览、数据预览或运行时预览，主要用于提前发现配置问题。它们不会替代 Runner 的真实执行，也不会自动生成完整 Run、Evidence 和报告。

真实执行统一从“运行中心”创建并派发，由在线 Runner 消费。

### 2.4 Runner 是实际执行端

后端负责权限、任务编排、版本快照、状态和结果持久化；Windows Runner 负责真实发 HTTP 请求、连接测试数据库、运行受限脚本以及驱动 Chrome。没有在线且能力匹配的 Runner，任务可以创建，但不能完成真实执行。

### 2.5 AI 始终受人工和结构化契约约束

AI 功能依赖四层配置：渠道连接、模型、项目任务绑定、Prompt/Output Schema。AI 输出需要通过结构校验；必要时只允许一次 Repair，并记录模型、Prompt 版本、Schema、Token、成本、延迟、Fallback 和 Repair 信息。

需求建议、Swagger 建议、Web 录制整理和 Locator 自愈都需要人工审核。确定性断言失败不能被 AI 结论覆盖；低置信或冲突结果进入 `REVIEW`。

## 3. 用户、角色与权限

### 3.1 平台角色

| 角色 | 典型权限 |
|---|---|
| `ADMIN` | 管理用户、Runner、全局模型渠道，并可访问业务管理功能 |
| `USER` | 使用被授权项目中的功能，不能进入用户管理和 Runner 中心 |

当前系统没有公开注册入口。用户由管理员在“用户管理”中创建。

### 3.2 项目角色

| 角色 | 适合人群 | 主要能力 |
|---|---|---|
| `PROJECT_OWNER` | 项目负责人 | 在项目门户管理资料和成员，在项目工作区维护运行配置，并管理测试资产和运行 |
| `TESTER` | 测试开发/执行人员 | 在授权项目内创建和维护测试资产、发起运行、查看结果 |
| `VIEWER` | 观察者、审计或干系人 | 只读查看项目资产、运行、证据和报告 |

平台角色与项目角色是两层权限。一个普通 `USER` 只有加入某个项目后才能访问该项目；同一用户在不同项目可以拥有不同项目角色。

### 3.3 当前本地开发账号

当前重建后的本地开发库仅初始化了一个平台管理员：

```text
用户名：admin
密码：admin123
```

该密码只用于本机首次登录。登录后应从右上角用户菜单进入“修改密码”。生产配置会拒绝默认密码。

## 4. 主流程总览

```text
管理员准备用户、Runner、模型与 Prompt
                    │
项目负责人创建项目、成员、环境、变量、Secret、数据库连接
                    │
       ┌────────────┴────────────┐
       │                         │
Markdown 需求                Swagger/OpenAPI
       │                         │
需求版本、AI 评审            API Definition 固定契约
       │                         │
AI Case 建议              AI Case / Scenario 建议
       └────────────┬────────────┘
                    │
     人工编辑、接受/拒绝、检查并按资产类型批准
                    │
 API Case / Scenario / Web Case + 可选数据集
                    │
          运行中心创建并派发 Run
                    │
      Runner 执行、实时状态、断言和 Cleanup
                    │
     Evidence → 报告 → 失败分析/自愈/缺陷草稿
```

最短可运行路径是：创建项目 → 配置环境 → 准备状态可执行的测试资产 → 注册并启动 Runner → 运行中心创建和派发 → 查看报告。

AI、数据集、数据库连接、Session Profile、自愈等能力都可以按场景逐步加入，不是最简单 Case 的强制前置条件。

## 5. 当前本地环境的首次使用顺序

当前代码和本地开发库迁移均为 `20260912_0055`；开发库由此前的 `20260911_0054` 空白基线完成非破坏性增量升级。项目、模型、Prompt、Runner 和历史运行仍以当前实际数据为准。

### 5.1 启动基础设施

1. 启动 Docker Desktop，等待 Engine 为 Running；
2. 启动 Redis、RabbitMQ 和 MinIO：

   ```powershell
   docker compose -f .\deploy\docker-compose.dev.yml up -d
   ```

3. 确认本机 MySQL 8.4 正在监听 `127.0.0.1:3306`；
4. 执行数据库迁移：

   ```powershell
   cd backend
   ..\.venv\Scripts\python.exe -m alembic upgrade head
   ..\.venv\Scripts\python.exe -m alembic current
   ```

5. `current` 应显示 `20260912_0055 (head)`。

### 5.2 第一次先只启动前后端

在 PyCharm 分别运行：

- `后端 FastAPI`
- `前端 Vue`

访问：

- 前端：`http://127.0.0.1:5173`
- 后端健康检查：`http://127.0.0.1:8000/health`
- Swagger UI：`http://127.0.0.1:8000/docs`

此时不要直接使用包含 Runner Worker 的“开发环境（一键启动）”，因为空库中还没有 Runner 身份。

### 5.3 完成基础管理配置

1. 用 `admin / admin123` 登录并修改密码；
2. 如有协作者，在“用户管理”创建用户；
3. 在“项目管理”创建项目并添加成员；
4. 进入项目工作区，在“运行配置”中创建环境、变量和必要的 Secret；
5. 若要使用 AI，再配置模型渠道、模型、Prompt、Output Schema 和项目任务绑定；
6. 若要执行 SQL，配置项目 MySQL 连接并测试连通性。

### 5.4 首次注册 Runner

1. 管理员进入“Runner 中心”；
2. 创建一次性 Registration Token，并立即安全保存页面显示的 Token；
3. 在项目根目录的 Terminal 执行：

   ```powershell
   cd runner
   ..\.venv\Scripts\python.exe -m runner.main register --backend-url http://127.0.0.1:8000 --name windows-runner --tag windows --api-slots 1 --web-slots 1
   ```

4. 在隐藏输入提示中粘贴 Token；不要把 Token 写进命令行、脚本、截图或文档；
5. 注册成功后执行：

   ```powershell
   ..\.venv\Scripts\python.exe -m runner.main heartbeat-once
   ```

6. 返回 `ACTIVE` 后，在 PyCharm 启动 `Runner Worker`。

本机可能仍保留重建数据库前的 DPAPI 身份文件，但数据库中的旧 Runner 已不存在，旧凭据不能继续使用。使用新 Token 注册成功后会写入新身份；不要手工打开、复制或打印身份文件。

### 5.5 以后日常启动

已经完成一次 Runner 注册后，日常顺序为：

1. Docker Desktop；
2. 开发 Compose 中间件；
3. 本机 MySQL；
4. 必要时运行迁移；
5. PyCharm 运行 `开发环境（一键启动）`。

## 6. 项目治理与运行配置

### 6.0 新版导航结构

登录后左侧菜单分为两种状态：

| 所在位置 | 左侧菜单 | 适合做什么 |
|---|---|---|
| 平台公共区域 | 项目门户、AI 主演示、平台概览、模型中心、Prompt 中心、Runner 中心、用户管理 | 选择项目，或维护多个项目共用的平台能力 |
| 项目工作区 | 项目概览、需求、API、测试用例、数据集、测试编排、Web 自动化、运行、报告、证据、缺陷、AI 审计、资源清理、运行配置 | 处理当前项目的测试闭环和运行依赖 |

推荐入口是“项目门户 → 进入项目”。进入后会切换到独立项目工作区：左侧只显示当前项目的业务目录，顶部单行显示“返回项目门户”、项目标识、当前项目切换器和项目状态。平台账号角色、修改密码与退出入口只在平台门户外壳显示，不在项目内部重复；新建测试用例只从左侧“测试用例”模块进入，不再提供顶栏重复入口。切换项目时回到新项目概览，避免把上一个项目的筛选条件带过去。

浏览器地址中的 `/projects/{projectId}/...` 是当前项目的权威上下文。页面仍会把 `project_id` 传给既有接口和深链，后端权限校验不变。旧的 `/requirements`、`/runs` 等平铺地址暂时保留兼容，但不再作为主导航入口。

### 6.1 项目门户

用途：创建业务隔离空间、分配负责人、归档或恢复项目。

基本操作：

1. 进入“项目门户”；
2. 新建项目，填写名称、唯一项目编码和描述；
3. 在项目行点击“成员”，添加已有平台用户并分配项目角色；
4. 点击“进入项目”，在专属项目概览查看推荐流程；
5. 打开“运行配置”，完善环境、变量、密钥、数据库连接和模型绑定；
6. 项目停止维护时在项目门户执行归档；需要继续时恢复。

项目编码以字母开头，可包含字母、数字、下划线和连字符。归档不会删除历史数据。

### 6.2 环境

环境定义目标系统的基础地址和运行上下文，例如 `dev`、`test`、`staging`。

使用方式：

1. 在项目工作区“运行配置”的“环境”页创建环境；
2. 填写名称和 Base URL；
3. 选择是否启用，并可设置默认环境；
4. 创建 Run 时选择目标环境。

API 请求可以使用相对路径，由环境 Base URL 解析；也可以按资产约束使用完整 URL。

### 6.3 环境变量

环境变量用于保存非敏感的可复用值，例如租户编号、普通查询参数或演示账号名。变量可按环境区分。

在测试资产中使用模板引用，例如：

```text
{{tenant_id}}
```

密码、Token、私钥等不能放入普通环境变量，应使用 Secret。

### 6.4 Secret

Secret 用于密码、API Key、Bearer Token、数据库密码等敏感数据，支持项目级或环境级作用域、启停和轮换。页面只显示掩码，不回显明文。

在支持的位置使用：

```text
{{secret.api_token}}
```

本机 Windows 使用 DPAPI 保护；服务器容器使用独立跨平台加密 Provider。不要把真实 Secret 写进 Case、日志、Prompt、截图或导出文档。

### 6.5 MySQL 连接

用途：为数据集只读查询、SQL Action、SQL 节点或 Cleanup 提供受控连接。

使用方式：

1. 先创建保存数据库密码的 Secret；
2. 在项目工作区“运行配置”的“MySQL 连接”中填写主机、端口、数据库、用户名等；
3. 密码字段引用已有 PASSWORD Secret；
4. 执行连接测试；
5. 测试通过后启用连接。

数据集来源只允许只读查询。用于 Cleanup 的写操作必须通过显式 Cleanup 配置和权限边界，不能把任意写 SQL 当作数据源查询。

### 6.6 项目成员

项目负责人可以在“项目门户”对应项目行点击“成员”，添加已存在的平台用户，并分配 `PROJECT_OWNER`、`TESTER` 或 `VIEWER`。先在“用户管理”创建平台用户，再添加为项目成员。成员治理不再放在项目工作区的运行配置中。

### 6.7 模型绑定

模型绑定决定某个项目的某类 AI 任务使用哪个主模型和备用模型。绑定前必须先在“模型中心”创建并启用渠道和模型。

连接验证只执行最小文本请求。真实业务调用还会渲染 Prompt 并校验 Output Schema；当 OpenAI 兼容服务明确拒绝原生 `json_schema` 参数时，平台会自动执行一次不携带该参数的兼容请求，但返回内容仍需通过平台侧 Schema 校验和至多一次修复。页面会显示后端返回的安全错误摘要，并针对超时、网络、API Key、服务商拒绝和结构校验失败给出不同处理建议。

需求“AI 用例”已经改为持久化异步任务：点击后立即出现“等待执行/正在生成”记录并关闭弹窗，浏览器无需等待模型；可以离开页面，稍后返回后点击“查看结果”。同一需求只允许一个进行中任务，失败原因会脱敏保存在记录里。其他真实 AI 生成暂使用 180 秒等待上限，模型连通性验证使用 75 秒，普通页面请求仍为 15 秒。

常见任务类型包括：

- 需求评审 `REQUIREMENT_REVIEW`
- API 文档评审 `API_DOC_REVIEW`
- AI 测试设计 `API_TEST_DESIGN`
- API Case 生成 `API_CASE_GENERATE`
- API Scenario 生成 `API_SCENARIO_GENERATE`
- Web Case 生成 `WEB_CASE_GENERATE`
- AI 断言 `AI_ASSERTION`
- Locator 自愈 `LOCATOR_HEALING`
- Web 失败分析 `WEB_FAILURE_ANALYSIS`
- 缺陷草稿 `DEFECT_DRAFT`

每类任务最多配置一个主模型和一个 Fallback。Fallback 只在超时、限流、服务不可用或网络错误等规定场景触发，不会无限重试。

`PERFORMANCE_ANALYSIS` 已作为 V1 性能测试能力落地：从完成态性能 Run 的脱敏指标快照生成解释和优化建议，平台确定性 SLA 结论不可被 AI 修改。`IMPACT_ANALYSIS` 仍是 V2 预留类型。

## 7. 需求管理

用途：导入和版本化需求，建立 Requirement Tree，并从需求生成可审核的测试建议。

### 7.1 导入需求

1. 选择项目；
2. 选择 Markdown 导入；
3. 按标题层级组织需求内容；
4. 预览解析结果；
5. 确认后保存需求树，并把整份需求文档直接发布为项目需求 V1。

后续点击“编辑需求树”统一修改整棵树，发布后形成完整文档 V2/V3，历史版本不被覆盖。需求节点本身不再各自维护业务 V1/V2；其内部技术修订只用于稳定关联测试用例、评审和运行快照。

### 7.2 查看需求详情

需求详情可查看：

- 当前节点内容与完整需求文档版本历史；
- 历史完整快照；
- 已关联的 Case 或其他资产；
- 影响范围；
- 相关运行和执行追踪。

### 7.3 AI 需求评审

前置条件：项目已绑定 `REQUIREMENT_REVIEW` 模型，并存在启用且任务类型匹配的 Prompt/Schema。

用途：在测试设计之前先做“需求可测性体检”。AI 会定位表述不清、互相矛盾、业务规则遗漏、异常分支缺口和无法验证的验收标准，并给出可编辑的验收标准建议。它不会自动修改需求，也不会直接生成正式测试用例。

操作流程：

1. 首次进入需求管理不会自动确认 AI 操作对象，必须先点击左侧需求树中的一个节点；仅由旧地址参数装载需求详情不算用户确认，未确认时“AI 评审”和“AI 用例”均不可用。只有从 API 测试设计或 AI 记录的明确入口进入时才会自动确认指定需求；
2. 选中需求及其固定版本后，在右侧带 AI 图标的“AI 评审”页签中点击“开始 AI 评审”；选择根需求或章节时会自动把全部有效子需求纳入评审范围；
3. 选择需求评审 Prompt，可选择带入父需求、兄弟需求，并填写本轮关注点；
4. 提交后平台立即创建后台任务，可以点击“关闭，后台继续”或离开页面；等待中、生成中、失败及完成结果统一保存在记录中心，右侧页签不再重复展示历史卡片；
5. 右侧“本需求评审记录”只显示当前需求；页面顶部“AI 记录”显示当前项目全部需求，并可在“评审记录 / 设计记录”之间切换。点击具体记录的“查看详情”会覆盖在记录弹窗上方；关闭详情后仍返回当前记录列表；
6. 在详情中查看清晰度、歧义、缺失规则、异常场景、可测试性、验收标准建议和总体结论。AI 结果生成成功后保存为草稿，可以人工修改并保存；确认无误后“确认评审”会冻结这份评审结论，“拒绝”会保留拒绝记录；
7. 已完成或失败的评审记录可从列表删除，等待中和生成中的任务受保护。删除不会改动需求内容，也不会删除底层模型调用审计；
8. 确认评审不会自动覆盖需求，也不会自动新增版本。若结论可直接接受，保留记录后即可在当前完整文档版本上做 AI 测试设计；若问题较多，在已确认评审详情点击“基于评审创建新版本”。编辑器仍展示完整需求文档，但只有本次所选需求及其全部下级可编辑，父级、同级和其他分支只作为上下文显示；修订后发布完整文档 V2，再选择复审或直接做 AI 测试设计。

### 7.4 编辑需求树与完整文档版本

1. 点击页面顶部“编辑需求树”，左侧会显示当前完整目录，右侧编辑选中节点的标题、类型和 Markdown 正文；
2. 每个节点右侧固定显示“+”和删除入口：“+”在该节点下新增需求，“根需求”增加一级需求，删除只把节点从即将发布的新版本中移除；按住行内拖动标识上下拖动，可调整同一父级下的顺序，不能用拖动改变父子层级；
3. 编号由目录位置自动产生。新增或移动后会实时重排，例如在第 5 项前插入新节点，原第 5～10 项自动变为第 6～11 项；稳定技术追踪号不会改变，也不在普通目录中展示；
4. 填写版本变更说明并点击“发布完整需求新版本”。一次发布包含整棵树的所有改动；没有必要也不允许为每个小需求分别发布业务版本；
5. 旧版本快照不可变。删除节点不会物理删除旧版本、测试关联、评审记录或运行快照。

从评审详情进入时，入口显示为醒目的“AI 辅助修订并创建新版”。编辑范围严格等于“发起评审时选中的需求 + 它的全部下级”，其他节点锁定，服务端也会拒绝范围外修改。工作台打开后自动在后台调用 AI，将清晰度、歧义、缺失规则、异常场景、可测试性和验收标准建议归属到具体需求，并生成以下四类规划：

- “内容修订”按需求聚合建议，左侧显示原始正文，右侧显示可手工编辑的 AI 修订稿；点击“应用本需求全部建议”后自动切换下一项；
- “新增需求”显示建议父级、插入位置、标题、类型和完整正文，可逐项或一键加入草稿，稳定需求编号在发布时分配；
- “删除需求”单独显示删除理由和下级处理方式，可逐项或一键标记为“新版中移除”，应用前确认且发布前可撤销；
- “待确认”保存 AI 无法可靠归属的建议，平台不会擅自修改需求。

规划任务复用项目已有的需求评审模型绑定，无需再配置 Prompt。由于需要同时分析完整评审范围和全部建议，这类长上下文任务使用独立的 300 秒调用上限，不受模型通用短超时过早中止。规划期间点击“关闭，后台继续”或右上角关闭只结束当前查看，不会取消后台调用；再次从同一条评审记录进入时，会恢复等待状态或直接展示已经生成的规划。工作台支持“全屏查看 / 退出全屏”，便于处理长需求树和左右对比。规划结果会随评审记录保存；应用建议后的未发布草稿和人工编辑仍只保留在当前窗口，关闭前按钮会明确提示“关闭，不保存草稿”。所有“一键应用”只修改修订草稿，最终点击“发布完整需求新版本”后才创建 V2/V3。删除只归档新版中的有效节点，旧版本、测试关联、运行记录和评审审计继续保留。若上游模型在 300 秒内仍未返回，任务会明确标记失败，可点击“重新生成规划”；新调用独立执行，原失败记录继续留在 AI 审计中。

### 7.5 AI 测试设计与用例建议

1. 在右侧带 AI 图标的“AI 用例”页签中，从醒目的“AI 测试设计”功能卡点击“开始 AI 设计”；弹窗立即出现并创建一条可追溯的后台设计记录，浏览器不需要一直等待模型；“关闭，后台继续”只关闭窗口，不取消任务；
   测试设计与后续用例生成均使用独立的 300 秒长任务调用上限。检查点确认页和 API 闭环推荐列表均默认每页显示 10 条，可切换为 20/50/100 条；分页只改变当前展示范围，不会丢失检查点，也不会清空 API 的跨页勾选状态。能力缺口始终完整展示，避免遗漏人工验证或测试工具建设事项。
   如果用例生成失败，生成记录提供“重新生成”，会恢复原设计方案、已选 API 和补充要求并回到最终确认步骤；再次提交会创建新任务，原失败记录继续保留。
2. `API_TEST_DESIGN` 模型任务阅读当前需求及其所有子需求，并结合项目内有效 API 契约提取验收检查点、推荐接口、角色、理由及覆盖关系；平台随后校验接口编号、检查点引用并补充必要的认证或清理依赖；
3. 核对 AI 提取的检查点和推荐的 API 闭环。用户可以取消不相关接口，但不能在项目存在接口时提交空集合；若模型或结构校验失败，页面会明确显示“规则候选”及安全原因，不会把确定性匹配冒充成 AI；
4. 选择内置 Prompt，填写可选补充要求，点击“创建后台生成任务”；
5. 弹窗立即关闭，“AI 生成记录”先显示“等待执行/正在生成”，此时可以离开页面；任务会保存所选 API 和检查点计划；
6. “AI 用例”功能卡中的“本需求设计记录”只显示当前需求；页面顶部“AI 记录”中的“设计记录”汇总当前项目全部需求的设计任务，可同时观察不同需求的等待、运行和完成状态，并跳回对应需求；已结束且未被后续用例生成引用的记录可以删除，正在运行或已进入生成链的记录不能删除；删除设计记录不会删除需求、正式用例或 AI 调用审计；测试设计调用使用 300 秒后台超时，超时后保留规则候选与可追溯原因；
7. 页面每 3 秒自动刷新，也可稍后返回手工刷新。右侧窄栏只显示 AI 生成历史；成功后点击对应记录的“查看结果”，打开宽幅结果中心。每条记录只展示本轮生成的数据，不会和其他轮次混合；结果中心支持全屏查看；
8. 结果中心顶部汇总本轮生成总数、待审核数、正式用例数、已拒绝数、检查点覆盖率和本轮 API 数。“生成用例”页签默认每页 10 条，可切换 20/50/100 条，并支持对建议逐条查看或编辑名称、优先级、Tag、步骤、预期结果和额外 Requirement 关联；审核抽屉可用上一条/下一条连续查看，关闭后返回当前结果中心；
9. 在结果中心勾选本轮草稿后，可以批量修改、删除、拒绝或保存为正式用例；单条也可以保存为正式用例。只有保存为正式用例后，才会创建测试用例及首个版本；“覆盖与缺口”页签展示本轮检查点覆盖、待补项和能力风险；
10. 保存成功后即进入统一的“测试用例”资产库，无需再走 AI 专属补录流程。建议在首次运行前检查配置；API Case 保持 `ACTIVE` 即可由运行中心选择，没有单独批准按钮。

建议详情会保留来源需求、实际模型、Prompt/Schema、AI 原值和人工编辑值，便于审计。模型通过 `coverage:CP-xx` 标签声明每条建议实际验证的检查点；平台据此统计覆盖，但不会把 AI 自评当成覆盖率。

设计结果按需求版本、测试设计 Prompt、API 契约指纹和用户指定接口缓存；输入未变化时再次打开会复用原记录，点击“重新分析”才发起新模型调用。用例生成只能引用同需求、同版本的设计结果，且所选 API 必须来自本轮规划。

平台中的可增长记录列表默认每页 10 条，可切换 20、50 或 100 条；服务端已有分页的列表继续采用服务端分页，其余轻量配置记录采用前端分页。需求树、场景节点、用例步骤、断言和导入预览不属于独立业务记录集合，不强行分页。

## 8. API 定义

用途：把 Swagger/OpenAPI 文档固化为可追溯的接口契约，并由契约生成测试资产建议。

### 8.1 导入 Swagger/OpenAPI

1. 选择项目并新建导入；
2. 提供有效的 OpenAPI 文档；
3. 预览解析结果；
4. 确认接口路径、方法、参数、请求体、响应和认证信息；
5. 保存导入版本。

每次导入形成固定快照。后续 AI 生成和 Case 来源都指向明确的导入版本，避免外部文档变化导致历史漂移。

### 8.2 查看 API 契约

接口详情用于查看：

- Method 与 Path；
- Query、Header、Cookie 和 Path 参数；
- Request Body 与 Content-Type；
- Response 状态和 Schema；
- 认证要求；
- 来源文档和版本。

### 8.3 用此 API 发起测试设计与场景编排

- 在某条 API 契约详情点击“用此 API 发起测试设计”，先选择该接口要验证的业务需求，再自动打开需求工作台的同一条 AI 设计流程。当前接口会被强制保留，其他认证、核心操作、结果验证和数据清理接口由 AI 推荐并经用户确认。这个入口不直接生成另一批 API Case。
- 页面顶部“AI 场景编排”只使用 `API_SCENARIO_GENERATE`，负责多个接口之间的调用顺序、变量传递和清理关系：选择固定导入版本 → 生成 → 编辑建议 → 接受或拒绝 → 生成 DRAFT Scenario → 到“测试编排”检查并批准。

因此，单需求 API Case 统一从需求页生成，跨接口流程从 API 页编排，避免两套入口生成含义相近但无法比较覆盖范围的用例。

## 9. 测试用例

“测试用例”主要管理 API Case 以及其不可变版本和来源关联。Web Case 在“Web 自动化资产”中管理。

正式测试用例只有一种后续生命周期。AI 建议经审核保存和人工新建都会创建项目内业务编号、`ACTIVE` 用例和不可变 V1，并共用相同的内容校验、版本、运行、报告及归档流程。列表中的“AI 生成 / 人工创建”只表示创建来源，不改变用例能力。人工新建可以在基础信息步骤选择一个或多个关联需求；AI 保存会自动关联发起测试设计的需求。两者创建后都可以在详情中查看“关联需求（含历史）”。

新建用例或创建新版本时，编辑器按左侧菜单分为“基础信息、请求配置、动作与清理、数据与断言、结果与说明”五步；右侧一次只展示当前步骤。可以使用“上一步/下一步”，也可以直接点击菜单跳转，切换时不会丢失已填写内容。Web/手工用例会自动隐藏不适用的 API 步骤。

### 9.1 API Request

可以配置：

- HTTP Method：GET、POST、PUT、PATCH、DELETE、HEAD、OPTIONS；
- URL 或相对路径；
- Query、Header、Cookie；
- Body：NONE、JSON、FORM_URLENCODED、MULTIPART、RAW；
- Auth：NONE、BEARER、BASIC、API_KEY；
- 超时和 Step Retry；
- 环境变量、运行时变量与 Secret 引用。

Multipart 文件内容受大小和安全限制。不要手写带错误 boundary 的 Content-Type，Runner 会生成 multipart boundary。

### 9.2 Pre Action

Pre Action 在 HTTP 请求前按顺序运行，可用于：

- `SET_VARIABLE`：设置运行时变量；
- `FAKER`：生成白名单内的测试数据；
- SQL：执行受控数据库准备；
- Python：运行受限脚本；
- `GET_TOKEN`：获取并保存认证信息；
- `REGISTER_RESOURCE`：登记后续需要清理的资源。

运行时 Context 有大小和字段限制。不要在普通变量或脚本输出中传递 Secret 明文。

### 9.3 Response Extractor 与 Post Action

响应返回后可以从 JSONPath、Header 或 Cookie 提取值，供后续动作、断言或 Scenario 节点使用。必填提取失败会使执行失败；可选提取可以使用配置的默认值。

Post Action 可继续设置变量、提取响应、执行受限 SQL/Python 或登记资源。动作执行顺序和结果会写入 Trace。

### 9.4 断言

确定性断言用于验证状态码、Header、JSON 内容、Schema、文本等。AI 断言需要项目绑定 `AI_ASSERTION` 模型和匹配 Prompt/Schema。

规则：

- 确定性断言失败时，最终不能被 AI 改成成功；
- AI 低置信或与规则冲突时进入 `REVIEW`；
- AI 调用及其来源会进入审计日志。

Expected 输入会即时同步。字符串可以直接输入，例如 `v1-demo`；数字、布尔值、对象和数组可以填写标准 JSON。新增断言的入口位于“数据与断言”步骤中的断言列表右上角。

### 9.5 Cleanup

Cleanup 用于删除本次测试创建的临时资源，可配置 API 或 SQL 清理。资源也可以通过 `REGISTER_RESOURCE` 进入资源登记表，按 LIFO 顺序清理。

建议每个“创建资源”步骤同时设计可重复、安全、范围精确的 Cleanup。不要依赖人工事后清库。

### 9.6 版本与可执行状态

完成配置后先执行校验或运行时预览。API Case 没有单独的批准动作：保持用例为 `ACTIVE`，运行中心会使用其当前版本。修改时创建新版本，不能改写历史执行版本；不再使用时将用例归档。

## 10. 数据集

用途：把外部数据固定为可预览、可追溯的版本，供 API Case 按行迭代执行。

### 10.1 支持的数据来源

- CSV：UTF-8，单文件最大 10 MB；
- Excel：`.xlsx`；
- Faker：仅允许平台白名单生成器；
- MySQL：通过项目连接执行受控只读查询；
- Runtime：由上游运行时上下文提供。

### 10.2 使用流程

1. 选择数据来源；
2. 上传文件、配置 Faker 字段或填写只读 SQL；
3. 预览列名、样例行和类型；
4. 确认后保存不可变数据集版本；
5. 在 API Case 中绑定数据集及具体版本；
6. 在运行中心执行时，Runner 按行生成 iteration；
7. 报告中查看数据集版本、行号、脱敏参数快照和每行结果。

源文件或数据库内容后续变化不会改写已保存版本。需要新数据时创建新版本。废弃数据集应归档，不要删除历史运行所引用的快照。

## 11. 测试编排

用途：把多个 API、控制流、SQL、脚本、提取、断言和清理动作组成一个 API Scenario。

### 11.1 节点与能力

V1 可使用的主要节点/动作包括：

- START、END；
- API 请求节点；
- IF / ELSE 条件分支；
- LOOP 循环；
- WAIT 等待；
- SQL；
- 受限 Python；
- 变量设置，以及通过 HTTP + EXTRACT 获取 Token 或其他运行时值；
- 确定性断言与 AI 断言；
- SQL/API Cleanup，并在执行链中登记相应资源清理状态。

### 11.2 典型编排

```text
START
  → 登录接口并提取 token
  → 创建资源并提取 resource_id
  → IF 检查业务条件
      → 查询详情
      → SQL 校验
      → AI 断言
  → Cleanup 删除资源
END
```

### 11.3 使用方式

1. 新建 Scenario；
2. 默认在“流程图”视图按执行顺序添加节点；实线表示顺序，虚线表示 `IF`、`ELSE`、`LOOP` 父子作用域，拖动节点可调整顺序；
3. 选择流程节点后在右侧设置名称、父节点、启停和失败策略，也可进入详细 JSON 配置或执行单节点调试；需要逐字段核对时切换到“列表”视图，两种视图编辑的是同一份 DSL；
4. 配置正常结束、失败和取消时的 Cleanup；
5. 执行 DSL 校验和预览；
6. 保存新版本并人工批准；
7. 在运行中心选择 `SCENARIO` 执行。

流程图不会绕过原有校验：`START`/`END` 不可通过拖动或节点操作破坏，父节点候选会排除循环引用；服务端保存前仍会再次验证执行顺序、父子层级、变量和节点配置。Scenario 共享有界 Runtime Context。循环次数、等待、脚本、SQL 和总执行时间均受限制，避免无限循环或失控任务。

## 12. Web 自动化资产

该页面包含 Web Case、Page & Element、录制工作台和 Session Profile。

### 12.1 Page & Element

用途：集中维护页面、元素和 Locator 版本，让多个 Web Case 复用同一元素定义。

Locator 支持 CSS、XPath、Text、Role、Label、Placeholder、Test ID 等策略，也可在 Case 中直接填写 Locator。一个元素可以保存按确定顺序尝试的多个 Locator；Runner 会记录每个候选的诊断信息。

修改元素或 Locator 会形成新版本。历史 Run 继续指向执行时固定的元素版本。

### 12.2 Web Case

Web Case 可以手工创建，也可以由录制结果经 AI 整理后生成。

主要动作：

- 导航：GOTO、RELOAD、BACK、FORWARD；
- 多标签页：NEW_TAB、SWITCH_TAB、CLOSE_TAB；
- 元素：FILL、CLICK、DOUBLE_CLICK、RIGHT_CLICK、CLEAR、HOVER、DRAG_DROP；
- 表单：SELECT、CHECK、UNCHECK、RADIO；
- 键盘：PRESS、ENTER、TAB；
- 等待：WAIT_ELEMENT、WAIT_URL、WAIT_TIME、WAIT_TEXT、WAIT_NETWORK_IDLE；
- 文件和下载：UPLOAD、DOWNLOAD；
- 浏览器状态：Cookie、Local Storage、Session Storage、受限 JS；
- 断言：Visible、Hidden、Exists、Enabled、Clickable、Text、URL、Attribute、Input Value、Title、Element Count、Download、Network Request、视觉比较、AI 语义。

浏览器配置可包含窗口大小、语言、User-Agent、代理和受限下载路径。文件路径和代理必须符合 Runner 所在 Windows 主机的安全约束。

### 12.3 录制工作台

用途：在受控浏览器会话中记录操作，再整理成可维护的 Web Case。

流程：

1. 选择目标地址或本地 Demo；
2. 创建录制会话；
3. 在受控页面中执行登录、输入、点击等动作；
4. 停止录制并检查事件；
5. 可使用 `WEB_CASE_GENERATE` AI 任务整理事件、参数和断言；
6. 人工编辑并接受整理结果；
7. 保存为 DRAFT Web Case；
8. 到 Web Case 中补全配置并批准版本。

录制内容可能包含业务数据。上传、Prompt 和展示都会经过限制与脱敏，但仍应使用测试账号和测试数据。

### 12.4 Session Profile

用途：复用已登录浏览器状态，避免每个 Case 重复登录。

配置步骤：

1. 准备并批准一个专用登录 Web Case 版本；
2. 创建 Session Profile，绑定环境和该登录版本；
3. Runner 执行登录流程，安全保存加密 Storage State；
4. 普通 Web Case 绑定 Session Profile；
5. 状态有效时直接复用；过期时自动重跑登录流程并对原步骤最多重试一次。

Storage State 是敏感资产，不应下载、复制、打印或直接存入项目文档。

### 12.5 Locator 自愈

自愈从失败 Run 发起，而不是自动改写 Case：

1. Web Run 因 Locator 失败或超时；
2. 在运行中心进入自愈入口；
3. 选择失败 Trace，填写必要说明，可附已有截图；
4. 系统按受控阶段生成 DOM/模型/视觉候选；
5. 发起候选验证 Run；
6. 人工拒绝或接受 Proposal；
7. 接受后生成新的 DRAFT Locator/资产版本；
8. 人工批准新版本；
9. 使用新版本重新执行。

旧版本、原失败 Run、候选、验证记录和 AI 调用均会保留。接受 Proposal 不会改写原版本。

## 13. Runner 中心

Runner 中心仅平台管理员可见，用于管理注册令牌、执行器身份、能力、标签、Slot、在线状态和撤销。

### 13.1 Registration Token

- Token 只显示一次，并且只能消费一次；
- 不要写进命令参数、环境文件、聊天、日志或截图；
- Token 泄漏或注册失败状态不明时，应撤销对应 Runner/Token 后重新生成；
- Runner 注册后使用独立 Credential，不再使用 Registration Token。

### 13.2 标签、能力和 Slot

- Tag 用于调度到合适主机，例如 `windows`；
- API Slot 执行 `API_CASE` 和 `SCENARIO`；
- Web Slot 执行 `WEB_CASE`；
- Slot 表示并行容量，不应随意调大；
- V1 建议本地使用 `api-slots 1`、`web-slots 1`。

### 13.3 在线状态

Worker 持续向后端发送心跳，在线状态通过 Redis 加速显示。Redis 不可用时可能显示 `UNKNOWN`，应结合 Worker 控制台和后端状态判断，不能把 `UNKNOWN` 直接当成离线或正常。

撤销 Runner 后，其旧 Credential 失效。需要重新使用时生成新 Token 并重新注册。

---

## 14. 运行中心

运行中心是所有真实测试的统一入口。

### 14.1 创建 Run

1. 选择项目；
2. 选择运行类型：`API_CASE`、`SCENARIO` 或 `WEB_CASE`；
3. 统一选择运行环境和能力匹配的 Runner；
4. API Case 可按名称或业务编号搜索，并多选、全选或清空 `ACTIVE` 用例；Scenario/Web Case 选择一个明确的 `APPROVED` 版本；
5. 配置允许的重试和执行参数；
6. 点击“校验并创建”；批量 API 用例会逐条校验，每个通过项分别创建一条 Run，某一项失败不会阻断其他项；
7. 在运行列表中单条点击“运行”，或点击“一键运行待执行项”扫描并确认当前项目全部 `CREATED` Run 后统一派发。批量运行会先统一检查 Runner，再将全部记录加入执行队列；Runner 按槽位顺序处理，某条用例执行失败不会阻止下一条。

“创建”与“派发”是两个动作。刚创建的 `CREATED` Run 尚未进入 RabbitMQ。

### 14.2 状态说明

| 状态 | 含义 |
|---|---|
| `CREATED` | 已保存，尚未派发 |
| `QUEUED` | 已进入队列，等待 Runner |
| `ASSIGNED` | 已被 Runner 领取 |
| `RUNNING` | 正在执行 |
| `CANCELLING` | 已请求协作取消，等待 Runner 收敛 |
| `SUCCESS` | 执行成功 |
| `FAILED` | 执行或断言失败 |
| `CANCELLED` | 已取消 |
| `TIMEOUT` | 步骤或总预算超时 |

节点还可能出现 `REVIEW` 或 `SKIPPED`。`REVIEW` 通常表示 AI 断言低置信或存在冲突，需要人工判断。

### 14.3 实时控制台

运行详情显示 Run、Case/Iteration、Step、Action Trace、断言、提取值的安全摘要和 Evidence。页面优先使用 SSE 接收事件，断线后自动重连或降级轮询；数据库终态是最终权威。

### 14.4 Cancel 与 Force Stop

- Cancel 是协作取消：Runner 在安全点停止并执行约定 Cleanup；
- Force Stop 用于失联、超时或无法协作结束的任务；
- Web 执行会清理所属 Chrome 进程树；
- 强制停止可能导致业务资源未完全清理，结束后应检查“资源登记”。

不要因为页面短暂未刷新而重复派发同一个 Run。先查看状态事件、Runner 在线状态和队列情况。

### 14.5 失败后的入口

根据失败类型可以：

- 查看步骤 Trace 和 Evidence；
- 生成 Web 失败分析；
- 对 Locator 失败发起自愈；
- 检查或重试资源清理；
- 从报告生成缺陷草稿；
- 修复资产后创建新版本并发起一个新 Run。

## 15. 资源登记

用途：追踪测试过程中创建、需要在结束时清理的临时业务资源。

资源一般由 API Case 的 `REGISTER_RESOURCE`，或 Scenario 的 Cleanup 执行协议登记。页面可以按项目、Run、状态和清理结果筛选。

使用方式：

1. 先查看资源详情和所属 Run；
2. 预览 LIFO 清理计划；
3. 确认 API/SQL 清理目标精确；
4. 对失败项选择允许的重试；
5. 执行清理并检查每项结果。

该模块是异常恢复和审计工具，不是日常批量删数据入口。不得用宽泛 SQL、通配 URL 或不明确的资源标识替代精确 Cleanup。

## 16. 测试报告

### 16.1 报告列表

可以按项目、运行类型、状态、环境和时间筛选。报告来自已创建的 Run，不需要手工再建一份报告实体。

### 16.2 报告详情

报告包含：

- Run 基本信息、环境、触发方式和状态；
- 固定 Case/Scenario/Web 版本及 Requirement/API 来源快照；
- Case、Iteration、Step 和 Action 结果；
- API 请求/响应安全摘要、提取和断言；
- Web 操作、Locator 尝试、浏览器结果和 Evidence；
- Cleanup 和资源登记结果；
- AI 断言、失败分析、自愈及调用审计链接；
- 执行耗时和错误分类。

敏感 Header、Cookie、Secret 和已知输入会脱敏。不要以管理员权限绕过展示边界去直接读取底层对象。

### 16.3 导出

支持 Markdown 和 HTML 导出。导出内容同样遵守权限和脱敏规则。Evidence 文件通过受保护下载接口获取，不在公开报告中暴露 Bucket 或对象路径。

## 17. 证据中心

用途：集中检索截图、Playwright Trace、Web Summary、日志或其他运行证据。

使用方式：

1. 按项目、Run 或证据类型筛选；
2. 查看安全元数据、大小、时间和所属步骤；
3. 使用鉴权下载；
4. 结合报告或失败 Trace 判断问题。

MinIO Bucket 为私有。页面中看到的是数据库元数据和受控下载入口，不应直接修改 MinIO 中的对象。项目归档后，历史 Evidence 仍可按权限只读访问。

## 18. 缺陷草稿

用途：根据失败或超时 Run 生成结构化缺陷描述，减少整理上下文的工作。

前置条件：配置 `DEFECT_DRAFT` 模型绑定和匹配 Prompt/Schema。

流程：

1. 选择一个失败或超时 Run；
2. 发起缺陷草稿生成；
3. 核对标题、环境、复现步骤、实际结果、期望结果和 Evidence 引用；
4. 人工编辑；
5. 复制内容或导出 Markdown；
6. 由人工提交到实际缺陷系统。

V1 只生成内部草稿，不会自动向 Jira、禅道等外部系统提交。

## 19. 模型中心

模型中心分为“接入渠道”和“模型配置”。

### 19.1 接入渠道

1. 新建渠道；
2. 填写 Base URL、鉴权方式和 API Key Secret；
3. 保存后执行连接测试；
4. 确认启用状态。

API Key 加密保存并只显示掩码。不要在名称、描述或日志中重复写入 Key。

### 19.2 模型配置

1. 从渠道导入或手工配置模型；
2. 设置模型标识、能力、上下文限制、价格等必要信息；
3. 启用模型；
4. 回到项目工作区“运行配置”，为各任务类型设置主模型和可选备用模型。

连接测试成功只表示渠道基本可用，不代表某个项目的 Prompt、Schema 和任务绑定已经完成。

---

## 20. Prompt 中心

用途：管理不同 AI 任务的 Prompt 及不可变版本。

使用流程：

1. 新建 Prompt，设置唯一 Code 和任务类型；
2. 编写系统/用户模板和变量；
3. 绑定适合该任务的 Output Schema；
4. 使用“渲染预览”检查变量替换；
5. 保存并启用版本；
6. 修改时创建新版本，不覆盖历史调用使用的版本；
7. 不再使用时禁用，而不是破坏历史记录。

Prompt 的任务类型必须与调用入口一致。例如 Locator 自愈不能使用需求评审 Prompt。结构化业务任务应绑定明确的 Output Schema，以便校验、Repair 和人工审核页面稳定工作。

## 21. AI 输出与审计

该页面主要面向管理员、开发者和审计人员，包含：

- Output Schema：创建和版本化结构化输出约束；
- 真实 AI 调用：用指定 Prompt、项目绑定和变量执行受控调试；
- 结构化校验：验证样例输出是否符合 Schema；
- AI 日志：查看模型、Prompt、Schema、Token、成本、延迟、状态、Fallback 和 Repair。

推荐配置顺序：

1. 创建 Output Schema；
2. 创建并启用绑定该 Schema 的 Prompt；
3. 配置渠道和模型；
4. 配置项目任务绑定；
5. 在此页面做一次最小真实调用；
6. 再到需求、API、Web 或运行页面使用业务入口。

“真实 AI 调用”会消耗外部模型额度并产生审计记录，不应当作无成本预览反复点击。

## 22. 用户管理、改密与退出

“用户管理”仅管理员可见，可执行：

- 设置 `ADMIN` 或 `USER`；
- 修改显示名、角色和启用状态；

所有用户都可以从右上角菜单修改自己的密码。正常退出会向服务器撤销当前 Session 并清除本机状态；若服务器撤销失败，页面会明确提示是否只做本地退出，二者含义不同。

## 24. 五条推荐实操流程

### 24.1 Requirement → API Case

1. 项目工作区“运行配置”准备环境；
2. 需求管理导入 Markdown；
3. 选择固定需求版本做 AI 评审；
4. 生成 AI Case 建议；
5. 人工编辑、接受或拒绝；
6. 测试用例中补全请求、认证、断言和 Cleanup；
7. 确认 API Case 为 `ACTIVE`，并通过运行前校验；
8. 运行中心创建并派发；
9. 查看报告、Evidence 和需求执行追踪。

### 24.2 Swagger → API Case / Scenario

1. API 定义导入 OpenAPI；
2. 核对固定契约快照；
3. 生成 Case 或 Scenario 建议；
4. 人工编辑并接受；
5. 在对应页面完善运行参数和版本；
6. API Case 保持 `ACTIVE`；Scenario 人工批准后真实执行；
7. 从报告返回查看契约来源。

### 24.3 API 业务链路

1. 配置环境、Secret 和可选 MySQL 连接；
2. 新建 Scenario；
3. 登录并提取 Token；
4. 创建资源并登记 `resource_id`；
5. 用 IF/LOOP/WAIT、SQL、Python 和断言完成验证；
6. 设置失败、取消和正常结束的 Cleanup；
7. 校验并批准；
8. 运行后检查每个节点、资源登记和报告。

### 24.4 Web 录制 → 执行 → 自愈

1. 录制真实测试操作；
2. 用 AI 整理并人工编辑；
3. 保存和批准 Web Case；
4. 运行中心选择 Web Runner 执行；
5. 查看截图、Trace 和 Summary；
6. 故意或实际发生 Locator 失败后发起自愈；
7. 验证候选并人工接受；
8. 批准新版本并重新运行。

### 24.5 数据驱动 API Case

1. 在数据集页面导入 CSV/XLSX 或配置 Faker/MySQL；
2. 预览并保存固定版本；
3. 在 API Case 中绑定数据集列到请求变量；
4. 确认 Case 为 `ACTIVE` 并通过运行前校验；
5. 运行中心执行；
6. 报告中逐行查看 iteration、脱敏输入和断言结果。

## 25. 本地 Demo 的用途

项目自带独立 Web 演示目标，适合练习录制、登录态、Web Case、证据和 Locator 自愈，不等同于平台前端本身。

管理员现在可以从左侧“AI 主演示”进入首次向导，只填写 OpenAI-compatible Base URL、模型名和 API Key。模型探测通过后，平台会自动创建 `AI_DEMO` 项目、本机 Demo 环境、需求/OpenAPI，以及需求评审、API 用例生成、AI 断言、Web 失败分析、缺陷草稿所需的 Prompt、Output Schema 和项目模型绑定。该入口仅在非生产环境开放，重复执行只更新保留名 Demo 配置，不复制资产；密钥加密保存且不回显。完整逐页流程参见[《内置 Demo 从零到完整闭环操作手册》](./内置Demo从零到完整闭环操作手册.md)。

启动：

```powershell
.\.venv\Scripts\python.exe -m demo.server --port 8765
```

访问：`http://127.0.0.1:8765`

Demo 登录：

```text
用户名：demo
密码：demo-pass
```

`demo / demo-pass` 是演示目标账号；`admin / admin123` 是平台开发管理员，不能混用。完整场景参见[演示系统使用说明](./演示系统使用说明.md)。

### 25.1 业务编号规则

## 26. Docker Desktop 中的数据分别在哪里

当前本机开发拓扑为：

| 数据 | 当前存放位置 | 管理方式 |
|---|---|---|
| 平台业务表、用户、项目、资产、Run 元数据 | Windows 本机 MySQL：`127.0.0.1:3306/ai_test_platform` | MySQL 工具、Alembic；默认不在 Docker Volume |
| Runner 在线态、实时事件和缓存 | Docker Redis Volume | Redis CLI/管理工具；不是长期业务权威库 |
| 待执行消息、队列和死信 | Docker RabbitMQ Volume | `http://127.0.0.1:15672` 管理台 |
| 截图、Trace、Summary 等 Evidence 对象 | Docker MinIO Volume | `http://127.0.0.1:9001` Console；业务访问应走平台受保护接口 |
| Runner 本机身份 | Windows 当前用户 `%LOCALAPPDATA%\AI Native Test Platform\runner` | 由 Runner CLI 和 DPAPI 管理，不手工编辑 |

Docker Desktop 的 Containers 页面用于启停容器，Volumes 页面用于查看持久卷。删除容器不一定删除 Volume；执行 `docker compose down -v` 会删除 Compose Volume，属于破坏性操作，不应用作普通“重启”。

当前旧验收数据备份位于项目根目录被忽略的 `.local-backups/`：

- MySQL：`.local-backups/database/ai_test_platform_0038_20260911T132332Z.sql`
- MinIO：`.local-backups/object-store/`
- 备份清单/快照：`.local-backups/snapshots/`

备份可能包含敏感测试数据，不要提交、公开、随意删除或直接当作当前开发库继续写入。

## 27. 常见问题

### 27.1 能登录，但页面没有项目

当前是空开发库，需要先创建项目；普通用户还必须被添加为项目成员。

### 27.2 Run 一直停在 QUEUED

依次检查：

1. Runner Worker 是否正在运行；
2. Runner 中心是否显示 ACTIVE/在线；
3. Runner 的 Tag 和 API/Web Slot 是否匹配；
4. RabbitMQ 是否健康；
5. Run 是否已显式派发，而不只是创建。

### 27.3 Runner 返回未授权

数据库重建、管理员撤销或本机身份变化后，旧 Credential 会失效。由管理员创建新 Registration Token，再执行注册命令；不要尝试恢复或打印旧 Credential。

### 27.4 AI 按钮不可用或调用失败

检查：渠道是否启用且连接测试通过、模型是否启用、项目任务是否绑定模型、Prompt 是否启用且任务类型匹配、Output Schema 是否匹配、外部 Provider 是否可达。

### 27.5 AI 建议已接受但运行中心找不到

先确认建议实际生成了哪类资产：API Case 需要为 `ACTIVE` 且配置合法；Scenario/Web Case 需要到对应页面批准为 `APPROVED`。还要确认当前项目、环境、Runner 能力和资产版本选择正确。

### 27.6 资产预览成功但真实执行失败

预览不一定访问真实网络、浏览器、数据库或外部 Provider。检查真实环境 Base URL、Secret、Runner 能力、网络、证书、数据库连接和 Cleanup 权限。

### 27.7 前端打开但登录失败

确认后端 `http://127.0.0.1:8000/health` 正常、数据库迁移为 `0055`，并检查浏览器网络面板中的 401 或代理错误。

### 27.8 Evidence 列表有记录但无法下载

检查当前用户是否仍有项目权限、MinIO 是否健康、对象是否存在，以及后端下载接口日志。不要绕过后端直接把 Bucket 改成公开。

### 27.9 取消后仍有未清理资源

Cancel/Force Stop 可能在业务动作中间发生。进入“资源登记”，按 Run 筛选并预览 LIFO 清理计划，再对失败项做受控重试。

### 27.10 为什么修改后看不到历史 Run 变化

这是预期行为。历史 Run 固定引用执行时版本；修改产生新草稿和新版本，批准后需要创建新 Run。

## 28. 推荐的日常操作纪律

- 每次先确认当前项目和环境，避免在错误目标上执行；
- 测试资产优先引用变量和 Secret，不复制敏感明文；
- AI 产物必须人工检查后再批准；
- 创建资源的测试必须同时设计 Cleanup；
- 已进入历史运行或已经批准的版本不直接改写，修复后创建新版本；
- 不重复派发状态不明的 Run；
- 报告、Evidence 和 AI 日志一起看，不只看最终红绿状态；
- 不在 Docker Desktop 中随意删除 Volume；
- 不用手写 SQL 修改 Alembic 版本或核心业务状态；
- 本地开发默认密码、Demo 密码和真实业务凭据严格分开；
- 归档用于停止新增并保留审计，不等于删除。
